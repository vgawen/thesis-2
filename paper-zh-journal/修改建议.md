Abstract: This paper studies a specific risk in LLM-assisted self-healing for Playwright tests: a repaired locator may remain syntactically valid and executable while pointing to the wrong element, causing a silent false heal. **0 引言**

用户界面测试的维护一直是 Web 工程中的长期成本。对 Playwright 这类端到端测试而言，CSS 类名调整、组件重构、节点嵌套变化，甚至不改变业务行为的前端重排，都可能导致原有定位器失效[1-4]。因此，如何在界面持续演化的条件下维持测试稳定性，已经成为自动化测试工程中的一个实际问题。

围绕这一问题，工业工具和研究工作通常将“测试自愈”作为应对路径：当既有定位器失效时，系统尝试自动生成新的定位方式，使测试继续执行[5-6]。近年来，大语言模型也被引入测试生成、修复和分析任务[7-8]，定位器修复因此成为一个较易落地的应用方向。

不过，现有讨论更常报告“是否修通”或“是否能够输出合法选择器”，对另一类风险关注不足：修复器虽然给出了可执行的选择器，但该选择器不再指向开发者原本意图操作的元素。这样产生的结果不是显式失败，而是“测试表面通过、语义实际偏移”。在持续集成环境中，这类误修复比直接失败更难察觉，也更容易掩盖真实的界面回归。

基于这一问题，本文在 ReproBreak[6] 数据集的 Playwright 失效用例上，对隐性误修复现象进行了选择器层面的实证分析。实验主要基于 tryghost/koenig 的 93 个失效配对展开，并使用 payloadcms/payload 作为跨应用对照。围绕这些样本，本文得到三点结果。第一，在目标元素被强制移除的对抗性设置下，朴素 LLM 修复器经常返回指向错误元素的可解析选择器，且在提示中增加“无合适候选则放弃”的约束并未改变这一结果。第二，在可达用例范围内，data-testid 加权检索和强锚点后置过滤这两项低开销确定性策略能够带来小幅增益，且未观察到回归。第三，跨应用表现与代码库中锚点约定密切相关；当静态抽取器不能处理 BEM 模板字面量等模式时，可达率会显著下降。

需要说明的是，本文统一采用“静态修复代理指标”而不是运行时端到端修复率。前者关注修复后选择器与目标元素的一致性，适合对误修复现象做局部诊断；后者则还受到可见性、时序和运行环境等因素影响。两者相关，但不能直接等同，因此本文将基于 Docker 的行为重放验证作为后续工作方向。

本文的主要贡献如下：1）在真实 Playwright 数据集上对隐性误修复进行了针对性测量，说明单看“修通率”不足以评估自愈效果；2）实现了一个可本地复现的 HealReact L1 静态基线，并给出其在 koenig 项目上的覆盖情况；3）通过双因子析因分析考察了两项确定性策略的边际作用，为后续自愈系统设计提供了较具体的工程依据。

**1 背景与相关工作**

**1.1 定位器脆弱性与基准数据集**

定位器脆弱性是 GUI 自动化测试中的常见问题。ReproBreak[6] 目前提供了规模较大的可复现 Web 定位器失效数据，包含来自 359 个仓库的 449 个可复现定位器失效。本文以 tryghost/koenig[10] 的 Playwright 测试切片作为主要评估对象，其中包含 93 个可复现失效，分布在 19 个提交中。

**1.2 自愈工具与修复思路**

测试自愈可以看作一种受约束的自动修复问题，即系统在既有测试语义下生成候选补丁，同时尽量避免引入新的错误行为。工业界的 Healenium 倾向于在运行时基于 DOM 相似性修复 Selenium 选择器。Joseph[5] 则基于可访问性树重新抽取定位器，是确定性修复思路的一个代表性例子。与这些工作相比，LLM 方案在表达和生成上更灵活，但其输出也更容易出现“形式正确、语义偏离”的情况。

**1.3 现有工作的不足**

从目前可检索到的相关工作看，已有研究更多关注修复成功率、通过率或生成结果的一致性，对隐性误修复比例缺少专门测量。Joseph[5] 的结果基于目标元素按构造可达的演示样例；ReproBreak[6] 提供了数据基础，但并未对具体修复器进行误修复分析。本文的工作重点，正是在真实失效样本上把“是否修通”和“是否修对”区分开来。

**1.4 React 场景中的锚点差异**

本文涉及的两个 React 代码库使用了不同的锚点约定。koenig-lexical[10,12] 的 Playwright 测试较多依赖自定义 `data-kg-*` 属性，而不是标准 `data-testid`。payloadcms/payload[13] 则大量使用 BEM 风格类名[14]，并通过 `${baseClass}__suffix` 形式的模板字面量构造 `className`。前者有利于静态锚点抽取，后者则会给纯文本 AST 抽取带来困难。这一差异也是后文跨应用分析的基础。

**2 HealReact L1 静态基线**

HealReact 被设计为一个分层流水线。L1 负责从源码中静态抽取候选元素；L2 负责补足仅在运行时出现的 DOM 元素；L3 在候选集上生成修复后的选择器；L4 则通过行为重放验证修复结果是否与原测试意图一致。本文主要实现并评估 L1 与 L3，L2 和 L4 在本稿中仍作为设计中的后续层。

图1展示了 HealReact 的整体流程。对本文而言，L1 的作用不是直接替代运行时验证，而是为后续修复与分析提供一个可复现的静态候选空间；L3 的作用是在这一候选空间上生成修复选择器；L4 的作用则是把“选择器能解析”与“测试语义正确”进一步区分开来。

**2.1 AST 抽取器**

L1 抽取器基于 ts-morph[15] 遍历目标目录下的 `.tsx` 和 `.jsx` 文件，并为每个交互相关 JSX 元素生成一条 LocatorSheet 记录。记录内容包括元素标签、父链、role、`data-testid`、`aria-label`、`id`、`className`、文本信息以及自定义 `data-*` 属性。抽取器并不限制于标准 HTML 标签，而是尽量保留那些带有稳定锚点的 JSX 元素。这样做的目的，是让静态候选空间更接近实际测试中可利用的定位信息。在 koenig-lexical 上，这一处理使锚点覆盖率和解析命中率都有明显改善。

**2.2 意图标注器与校准器**

除了锚点抽取，HealReact 还设计了一个意图标注流程。系统通过 Ollama[16] 调用 Qwen2.5-3B，结合组件源码与 JSX 上下文，为交互元素生成功能性意图标签，例如 `submit-order-button`。随后，确定性校准层用十条规则识别可能不可靠的标签，例如兄弟元素标签塌缩、名词化退化以及 `role` 与意图不一致等情况。被标记的记录会提交给 Qwen2.5-Coder-7B 重新标注。需要强调的是，本文后续关于真实失效用例的定量评估主要依赖静态锚点和词法检索，不依赖这一意图层，因此该部分在本文中更接近架构说明而非核心实验变量。

**2.3 选择器解析器与判定标准**

为了比较修复结果与真值选择器，本文实现了一个 Playwright 选择器解析与匹配器。该解析器能够处理 `page.locator`、`getByTestId` 和原始 CSS 等常见表达方式，并将其映射到 LocatorSheet 中的记录。本文中“可达”是指失效选择器在静态候选空间内是否存在对应目标；“修复正确”是指修复后的选择器与真值选择器是否映射到同一元素。早期版本的解析器曾高估可达率，本文已在效度审计中收紧相关假设，并在后文单独报告宽松和严格两种设定下的结果。

**2.4 核心指标**

在 koenig 的 19 个失效提交上，抽取器平均每个提交生成约 400 条 LocatorSheet 记录，范围为 314 至 489。按照本文采用的宽松解析设定，L1 对 93 个真实失效目标中的 75 个实现了静态覆盖，对应可达率为 80.6%。其余 18 个样本主要依赖运行时动态渲染，属于静态抽取难以覆盖的情形，这部分更适合由后续的 L2 层处理。

**3 实证结果**

下述结果均基于同一套实验脚本、统一的数据记录方式和相同的判定规则。为了减少解码波动，所有模型调用均固定 `temperature=0`。

**3.1 实验配置**

L3 修复器和意图标注器分别通过 Ollama 调用 Qwen2.5-Coder-7B 与 Qwen2.5-3B。候选检索采用加性词元重叠打分，`testId` 权重设为 3，`dataAttr` 键值对权重设为 2，基础属性如 `aria`、`id`、`class`、`text` 和 `path` 权重设为 1，并保留前 k 个候选元素。对每个失效用例，实验记录其原始失效选择器、真值选择器、模型输出、解析结果以及最终判定。相关脚本、结果记录和数据快照已公开归档在 GitHub 仓库中，表1至表5中的统计值可以由该归档复算。

**3.2 L3 的统一输入输出协议**

在各项实验中，L3 接收三部分输入：原始失效的 Playwright 选择器、失效行附近的测试源码，以及经检索得到的 LocatorSheet 候选元素。模型按照统一格式输出三行内容：`SELECTOR`、`CANDIDATE_IDX` 和 `RATIONALE`。在出现多重匹配时，解析器按 `(componentFile, line)` 顺序选取首次命中作为比较对象；这类情况会被单独标记，但定量统计仍以首次命中为准。

**3.3 目标缺失条件下的隐性误修复**

**3.3.1 实验设置**

针对 koenig 中 75 个可达失效用例，本文构造了一个对抗性探针：在保持其他输入不变的前提下，从 LocatorSheet 和候选集中移除真值元素，从而排除模型命中正确目标的可能。在这种设置下，合理响应应当是触发放弃机制，即输出 `CANDIDATE_IDX:-1`；如果模型仍返回能够被解析的选择器，则说明它将测试重写到了错误元素上，可视为一次隐性误修复。

本文比较了两种提示变体。其一为基线提示，即 L3 默认使用的系统提示。其二在原有基础上增加“如无合适候选则放弃”的显式约束，用以观察提示强化是否会改变模型行为。

**3.3.2 实验结果**

结果见表1。两种提示变体在 75 个用例上的聚合统计完全一致：13 个用例选择放弃，59 个用例产生误修复，3 个用例输出未能解析。对应的误修复比例为 78.7%（59/75）。表2进一步给出了逐用例配对结果。可以看到，两种提示变体在每个样本上的判定都一致，而不只是汇总数字相同。

**3.3.3 结果解释**

这一结果说明，在目标元素缺失的对抗性设置下，朴素 LLM 修复器倾向于继续给出某个“看起来可用”的选择器，而不是主动放弃。更重要的是，在本实验中，增加“无合适候选则放弃”的提示并未改变模型的外显行为。因此，如果系统希望可靠地区分“可以修”与“不应修”，更稳妥的做法通常不是继续叠加提示词，而是在模型外部设置约束，例如检索分数阈值、锚点类型规则或运行时验证器。

需要强调的是，78.7% 是在对抗性构造下得到的上界，不应直接视为真实部署环境中的误修复率。结合 koenig 中 93 个失效样本里有 18 个目标在 L1 中不可达这一事实，可以得到一个粗略的风险估计：只有静态候选空间缺失真实目标的用例才会暴露出这类问题。因此，这一数字更适合作为风险提醒，而不是部署层面的实测结论。

**3.4 L3 基线与两项确定性策略**

**3.4.1 实验设置**

在同一组 75 个可达 koenig 用例上，本文比较两个 L3 变体。`v0` 为基线版本：候选元素仅按词元重叠度排序，不对 `testId` 进行额外加权，也不使用后置过滤。`v1` 在此基础上增加两项策略：一是对 `testId` 匹配提升检索权重；二是在候选携带可静态求值 `testId`、而模型输出却未使用该锚点时，按规则重写为 `getByTestId(testId)`。为了分离两项策略的独立作用，本文采用双因子析因设计，完整运行四个实验组。

**3.4.2 实验结果**

表3给出了 `v0` 与 `v1` 的整体对比，表4给出了双因子析因结果。与 `v0` 相比，`v1` 在 75 个可达用例上的 Top-1 精确匹配由 55 个提升到 58 个；有效 Playwright 选择器数量保持不变；按 93 个全量样本计算的静态修复代理指标由 59.1% 提升到 62.4%。从表4可见，单独启用 `testId` 加权或强锚点过滤时，精确匹配都增加 2 个；两者同时启用时，累计增加 3 个，且未观察到回归样本。按照 McNemar 精确检验，这些差异在当前样本量下尚未达到统计显著。

**3.4.3 结果解释**

这两项策略都属于实现成本较低的确定性改动，本质上分别对应检索权重调整和简单的输出后置规则。从结果看，它们可以在不引入已观察回归的前提下带来小幅改进，尤其有助于减少“模型选中了正确候选，但最终输出绑定到了不稳定锚点”的情况。考虑到样本量有限，本文更愿意把这两项策略视为局部有效的工程经验，而不是已被统计显著性充分支持的一般性结论。

**3.5 跨应用泛化与 BEM 盲区**

**3.5.1 实验设置**

为了观察结果是否依赖单一项目的锚点习惯，本文选取 payloadcms/payload[13] 作为第二个 React+Playwright 代码库进行对照。在不修改 L1 抽取器的前提下，本文对其 `packages/ui/src` 目录执行静态抽取，共得到 457 条记录，并对 319 个失效配对做 `new_locator` 解析匹配。

**3.5.2 实验结果**

结果见表5。与 koenig 的 80.6% 可达率相比，payload 的原始可达率仅为 3.8%。对 307 个未命中样本的追溯显示，其主要原因与锚点表达方式有关：payload 广泛使用 BEM 风格类名，并通过 `baseClass` 常量与模板字面量拼接得到最终 `className`。测试脚本引用的是渲染后的类名，而纯静态字面量抽取器难以恢复这一展开结果。

**3.5.3 结果解释**

这一结果更像是当前实现边界的暴露，而不是对静态方法本身的否定。对这类样本，较直接的改进方向是为抽取器补充模板字面量展开、`baseClass` 回溯以及 CSS Modules 等规则。换言之，跨应用泛化能力并不只取决于修复模型本身，也取决于系统能否适应不同项目对测试锚点的编码习惯。若只在单一项目上评估，很容易高估方法在其他代码库中的表现。

**4 讨论与局限**

**4.1 对无人值守 CI 自愈的启示**

如果一个自愈系统在测试失败后自动生成补丁，并直接由 CI 提交修复结果，那么最需要防范的不是“修不好”，而是“修到别处但仍然通过”。对本文所观察的问题而言，构建失败通常会暴露风险，语义偏移而未被发现才更值得警惕。因此，在缺乏运行时验证的情况下，直接提交 LLM 生成的选择器补丁并不稳妥。

**4.2 为什么提示强化没有起作用**

在本文设置下，增加“无合适候选则放弃”的提示并未改变逐用例输出。一个可能的解释是：对于代码模型而言，“给出一个形式完整的答案”往往比“承认当前无法修复”更符合其默认生成倾向。不过，这里只是一种基于现象的解释，本文并未进一步验证其训练层面的原因。对工具设计来说，更重要的结论是：放弃机制如果要可靠工作，最好建立在模型外部，而不是完全依赖提示词约束。

**4.3 为什么确定性策略更稳定**

与提示工程相比，`testId` 加权检索和强锚点过滤直接作用于候选空间或最终输出，因此行为更透明，也更容易验证。它们并不能从根本上解决误修复问题，但在当前样本上表现出较好的可控性。就工程实践而言，这类规则化改动往往更适合作为安全层，而把模型放在候选排序和表达补全的位置上。

**4.4 局限**

本文仍有几方面局限。第一，模型评估主要基于 Qwen2.5-Coder-7B；更大模型是否能显著降低误修复风险，尚需进一步实验。第二，核心定量结果主要来自 koenig，尽管引入了 payload 作为对照，但后者的可达率受到当前抽取器实现边界的限制。第三，本文报告的是选择器层面的静态代理指标，而不是端到端运行时通过率。作为小规模验证，本文对 3 个静态精确匹配样本进行了 Docker 重放，其中 2 个补丁运行通过、1 个失败。这说明静态匹配和运行时通过之间有关联，但不能直接等同。

**4.5 有效性威胁**

本文的多个核心指标依赖于选择器解析器的判定边界。尤其是，若将动态属性值视为潜在匹配，或对复合 CSS 采用较宽松的祖先近似，可达率会明显上升。为此，本文增加了宽松与严格两组敏感性结果。按宽松设定，koenig 的 `new_locator` 可达率为 80.6%（75/93）；按严格设定，则为 54.8%（51/93）。因此，更合理的做法是把 L1 静态可达率理解为一个区间，而不是单点数值。后续若能结合真实 DOM 快照做抽样交叉校验，将有助于进一步收紧这一评估范围。

**4.6 后续工作**

接下来的工作有两个较直接的方向。一是扩展静态抽取器，使其能够处理更多跨项目常见的锚点表达方式，例如 BEM 模板字面量和 CSS Modules，从而提升可达率的稳定性。二是补齐 L4 行为验证层，在修复补丁落地前增加运行时重放验证，以减少“选择器可执行但语义不一致”的风险。

**5 结论**

本文围绕 Playwright 测试自愈中的隐性误修复问题进行了选择器层面的实证分析。结果表明，在目标元素缺失的对抗性设置下，朴素 LLM 修复器经常返回指向错误元素的可解析选择器；单纯在提示中增加放弃约束，并不足以改变这一行为。在 koenig 数据上，HealReact 的 L1 静态基线能够覆盖多数真实失效目标；在可达用例范围内，两项低开销确定性策略带来了小幅改进，且未观察到回归。与此同时，payload 的对照结果说明，代码库中的锚点约定差异会显著影响跨应用表现。综合来看，如果希望把 LLM 引入测试自愈流程，更稳妥的方案应当是“静态候选约束 + 确定性安全规则 + 运行时行为验证”，而不是仅凭模型生成结果直接完成无人值守补丁提交。
